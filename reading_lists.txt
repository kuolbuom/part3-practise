This exercise builds on the database migrations you have just completed. The important concept is learning how to create a many-to-many relationship using a join table.

Let's understand the database design first, then implement it step by step.
1. Understand what we are building
Currently, your database has two main tables:
- users – stores registered users.
- blogs – stores blogs.
Now we need a third table:

- reading_lists – connects users with blogs and stores whether each blog has been read.

For example:
users
        id	      username
        1	        kuol
        2	        john


blogs
        id	      title
        1	        Learn React
        2	        Learn PostgreSQL
        3	        Learn Docker


reading_lists
                 user_id	   blog_id	  read
                 1	         1	        false
                 1	         2	        true
                 2	         1	        false


Notice something important:
- Kuol has added two blogs to his reading list.
- John has added one blog.
- The same blog can appear in different users' reading lists.
- Each user can have a different read/unread status for the same blog.

3. What columns should the join table have?
We need four important columns:
Column	         Purpose
id	             Unique reading-list record
user_id	         Identifies the user
blog_id	         Identifies the blog
read	           Tracks whether the user has read the blog

The read column should default to false.

Why? Because when a user adds a blog to their reading list, they haven't read it yet.

Let's break it down:
Code	                              Meaning
user_id	                            Column in reading_lists
type: DataTypes.INTEGER	            Stores an integer
allowNull: false	                  Cannot be empty
references.model: "users"	          References the users table
references.key: "id"	              References the id column in users
onDelete: "CASCADE"	                If the referenced user is deleted, their reading-list records are also deleted

Visual explanation
users table (parent)
id Primary key
username

reading_lists table (child)
user_id Foreign key

blog_id
user_id references users.id

We'll do this step by step, keeping your existing code intact.
1. Understand the relationship
We now have three models:
- User
- Blog
- ReadingList

Think of ReadingList as the connection between a user and a blog.
For example:
{
  "userId": 3,
  "blogId": 5
}
This means user 3 wants blog 5 in their reading list.

Understand the new association
This is the important part:
User.belongsToMany(Blog, {
  through: ReadingList,
  as: "readings",
  foreignKey: "userId",
  otherKey: "blogId",
});


- belongsToMany(Blog) means one user can be associated with many blogs.
- through: ReadingList tells Sequelize which join table connects them.
- as: "readings" gives us the name we can use when querying the user's reading list.
- foreignKey: "userId" identifies the user column in the join table.
- otherKey: "blogId" identifies the blog column.
We retain your existing User.hasMany(Blog) association because it represents a different relationship.

1. Create models/readingList.js.
2. Update models/index.js.
Then start your application:

Understand the important part
Look at this statement:

  userId,
  blogId,

What happens here?
1. Sequelize receives the two IDs.
2. It inserts them into the reading_lists table.
3. The database automatically generates the id.
4. The read column automatically receives false because of our default value.
We don't need to supply read: false manually.

Notice the improvement:

23. Better bookkeeping.
Exercise 23 introduces an important security concept: a user must only be allowed to update their own reading-list entries.

For example:
- User 1 owns reading-list entry id: 1.
- User 2 tries to update entry id: 1.
- The application must reject User 2, even if they know the entry's ID.
We will use your existing userExtractor middleware to identify the logged-in user from the JWT token. It makes the authenticated user available as req.user. 
Step 1: Add the PUT route
Open controllers/readinglists.js.

At the top, add this import:
const { userExtractor } = require("../util/middleware");


Now add this route below your existing POST route:
router.put("/:id", userExtractor, async (req, res, next) => {
  try {
    const readingList = await ReadingList.findByPk(req.params.id);

    if (!readingList) {
      return res.status(404).json({
        error: "Reading list entry not found",
      });
    }

    if (readingList.userId !== req.user.id) {
      return res.status(403).json({
        error: "You can only update your own reading list",
      });
    }

    if (typeof req.body.read !== "boolean") {
      return res.status(400).json({
        error: "read must be a boolean",
      });
    }

    readingList.read = req.body.read;

    await readingList.save();

    res.json(readingList);
  } catch (error) {
    next(error);
  }
});


Understand the important part
This is the security check:
if (readingList.userId !== req.user.id)


Think of it like this:
Reading-list entry
Entry owner

userId = 1


Logged-in user
JWT identifies

req.user.id = 1

Same user — update allowed

If the logged-in user has id = 2, the request is rejected with 403 Forbidden.

Exercise:
24. More control.

This is the next reading-list improvement: filter a user's reading list based on whether each blog has been read.

You need to support three requests:
Request	Expected result
GET /api/users/1	All reading-list blogs
GET /api/users/1?read=true	Only read blogs
GET /api/users/1?read=false	Only unread blogs

We'll build on your existing GET /:id route.
Step 1: Update controllers/users.js
Inside your GET /:id route, before User.findByPk, add:
const readingListWhere = {};

if (req.query.read === "true") {
  readingListWhere.read = true;
} else if (req.query.read === "false") {
  readingListWhere.read = false;
}

Why compare with strings?

Query parameters arrive as strings, not JavaScript booleans.

For example:
req.query.read === "true"  // true
req.query.read === "false" // false


Step 2: Update the through option
Find your existing include:
include: {
  model: Blog,
  as: "readings",
  attributes: { exclude: ["userId"] },
  through: {
    attributes: ["id", "read"],
  },
},


Change only the through section:
through: {
  attributes: ["id", "read"],
  where: readingListWhere,
},


Your complete include becomes:
include: {
  model: Blog,
  as: "readings",
  attributes: { exclude: ["userId"] },
  through: {
    attributes: ["id", "read"],
    where: readingListWhere,
  },
},


Keep your existing code that renames ReadingList to readingList.
Step 3: Test the three requests
Since your reading-list entry is currently marked read: true, these are the expected results:

GET http://localhost:3000/api/users/1

Test B — Read blogs

Expected:

The important concept is through.where: it filters the records in the join table (reading_lists), rather than filtering the blogs themselves.
